# 開発方針と比較検討（日本語サマリー）

## 先行事例

1. **RV（madeye/rv）**: 今回の要求と最も近いRustネイティブVNCクライアント。GPUIを利用。ダーク/ライト、ホスト管理、フルスクリーン、Mac ARD認証、Keychain、VeNCryptおよび圧縮方式の実装がREADMEに記載される。MIT。既存のRFB実装を有効利用する最有力候補。ただしGPUI・依存関係がVentura 13.7.8 Intelで利用可能か要実機確認。
2. **IronVNC**: Rust+egui。Tight、ZRLE、CopyRect、RA2等をREADMEに記載。描画とコーデックの参考になるが、保存情報やバージョン、品質管理は別途レビュー。MIT/Apacheを確認。
3. **DeskVNC**: Rustコア+Tauri 2。VNCだけでなくRDP/SSHの総合クライアント。暗号化・Apple認証・継続更新の参考になるが、多機能で今回の「軽量」要求には範囲が広すぎる。
4. **TigerVNC**: 高成熟度のC++/FLTKクライアント。動作比較に重要だがGPLライセンスを理解せずコードを取り込まない。
5. **RealVNC / Jump Desktop / Apple画面共有**: UI/操作の研究対象。商用コードの流用はしない。

## 主な選定理由

- GPUI採用でRVをフォークすると最短で機能を得られる可能性があるが、Intel Ventura対応の実測がないため、現時点で採用を確定しない。OpenCodeが互換性調査を行い、既存資産再利用の利点が大きければADRを更新して切り替えてよい。
- egui/eframeはRustだけでUI・背景処理・CLIを構成しやすい。Tauri/WebViewよりブラウザ層が少なく、OpenCodeのRust実装に集中できる。ただし最速と断定せず実測する。
- ネットワーク解析・Keychain・設定データをGUIから分離すると、GUIバックエンドを将来交換しても認証や再接続を再実装する必要が少ない。
- 初期は高機能VNCサーバーへの対応を無理に約束しない。小さな動作する核を整えてからTLS、Mac認証、コーデックを追加する。

## 解像度と実測

- 1920×1080のRGBAフレーム約7.9MiB、3840×2160で約31.6MiB、5120×2880で約56.3MiB。送受信・復号・表示で複数コピーすれば、Intel Macのメモリ/CPUを圧迫する。
- よってP3で**差分矩形の保持とGPUへの領域転送**を設計の中心にする。p95操作遅延、実フレームレート、CPU/GPU使用率、メモリの安定性を実機で計測。
- Retinaの点座標とピクセル座標を混同しない。画面比率と余白を考慮してクリック位置を変換する。

## キー入力

- AppleのCommand/Option/Control/Shiftの修飾キーとRFB/X11キーシムを区別。Mac→Windows/LinuxでCommand→Ctrlを既定マッピングにする案を採用。
- JISキーボード、かな/英数、IME、Unicodeと物理キーの違いはネイティブAppKitイベントで検証。
- フォーカス喪失や通信断では押下状態を解除し、リモート側にキーが押しっぱなしとして残らない状態遷移を作る。

## セキュリティ

- VNCパスワードだけでは通信路が暗号化されない。安全な初期設定は**直接接続をlocalhostへ制限**する方式。非localhostへの未暗号化接続はプロファイル単位の明示許可が必要。
- 将来はTLS/VeNCrypt等を実装・検証し、証明書不一致や認証失敗時に自動ダウングレードしない。
- 機密情報をプレーンテキストの設定に残さず、Keychain保存とコード署名によるアクセス制御を重視。

## 最終目標と現状

最終目標は、低CPU/低メモリで滑らかなフルスクリーン、確実な再接続、GUI/CLI両対応、高解像度、暗号化、特殊キー・IME対応、クラッシュ耐性、配布可能なx86_64 `.app`。**このキットは仕様とP0基礎実装を含むが、P1–P5は今後OpenCodeが実装・実機検証する。**
